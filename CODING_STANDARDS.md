# Coding standards: `better-auth-waitlist`

These rules are enforceable: a PR that breaks one should be sent back. Terms are defined in [`CONTEXT.md`](./CONTEXT.md).

## Gating

1. **Gate in `databaseHooks.user.create.before`, returned from the plugin's `init()`.** This is the one point every user-creation path goes through (email/password, OAuth callback, id-token, email OTP, magic link, anonymous, admin `createUser`, ...). Never gate sign-up with a request hook (`hooks.before` on `/sign-up/email` or any other path): it misses every other path, so a request-level hook that refuses a sign-up would leave the gate open on every other method. The only other hooks are the three that carry the gate to a Guest (a user with no account, written by the host outside sign-up), and none of them refuses a sign-up: `hooks.before` on `/sign-up/email` (`src/claim.ts`) only lets an admitted Guest claim their row and otherwise passes the request to core; `hooks.before` on `/request-password-reset` and `databaseHooks.account.create` (`src/reset-guard.ts`) only stop a password reset giving an unadmitted Guest a login. `gate.test.ts` ("gate shape") pins exactly these: `databaseHooks.user.create` and `.delete`, `databaseHooks.account.create`, and the two request hooks with their paths.
2. **Never block sign-in.** The gate runs on user _creation_ only. No `session.create.before`, middleware or hook may deny a session to a user who already exists, whatever their entry's Status.
3. **Throw, don't return `false`.** Reject with `APIError.from(status, WAITLIST_ERROR_CODES.X)`. Returning `false` from the hook surfaces as a generic `FAILED_TO_CREATE_USER`. Note that Better Auth turns a **403** thrown during email sign-up into its generic success response when `requireEmailVerification` is on or `autoSignIn` is false; pick the status deliberately and test both configurations.
4. **Never trust the client for gating.** Waitlist fields added to core tables use `input: false`. Status is never settable through a public endpoint.

## Data model

5. **Position is derived from ordering, never stored.** Compute it at read time from the ordering (join time, then a stable tiebreaker such as `id`). No `position` column, no renumbering on approve/remove.
6. **Explicit Status state machine.** Declare the states and the allowed transitions in one place (a transition table). Every write that changes Status goes through one function that checks the transition and rejects anything else. No ad-hoc `update({ status })` elsewhere. Test every allowed transition and at least one forbidden one.
   - 6a. **Database access lives in `entries.ts` and `state-machine.ts`.** No other module touches `.adapter` or names an adapter source (`currentAdapter`, `getCurrentAdapter`, `runWithAdapter`, `runWithTransaction`); the data modules reach the adapter through `(await currentAdapter(context)).<method>(...)`, never a variable, so the guard sees every method (it resolves aliases such as `const db = currentAdapter` and variables that hold an adapter); endpoints, access and callbacks call those two. Rows are created only by `transition()` (`adapter.create` in `state-machine.ts`). Other writes are single-row `incrementOne` calls whose `where` is the guard, or `consumeOne` for delete. A status change guards on the `version` it read. Never `update` / `updateMany`, which can overwrite a concurrent transition. The one exception is `unlinkReferralsOf` in `entries.ts`: an `updateMany` that only sets `referredById = null` where it points at an entry just erased, so it can't undo a transition; it is listed by name in the guard's `ALLOWED_UNGUARDED`, and any other `update` / `updateMany` (or that one moved to another function) fails it. `src/tests/write-paths.test.ts` checks all of this on the syntax tree (comments and strings don't count). `TransitionPatch` rejects `status` and `version` at the type level.
7. **Invite codes:** generated with a CSPRNG (`generateRandomString` from `better-auth/crypto`); only a **hash** is stored, compared in constant time; **single-use** (consumed atomically, e.g. `consumeOne` or a guarded update, so two concurrent sign-ups can't both use it; the gate's `claimInvite` is a guarded write on the creation's transaction when there is a real one (`inRealTransaction`); without one nothing could undo a claim, so the gate only checks and `register` uses the invite up after the user exists, and single-use rests on the email binding plus the unique `user.email`; a `registered` entry never admits); **bound to one email** (normalised, lowercased) and rejected for any other; carry an **expiry** that is checked on use. Never log or return a stored code.
8. **Emails are normalised** (trimmed, lowercased) before every write and lookup.
9. Use logical model and field names through `ctx.context.adapter` (or `getCurrentAdapter` inside transactions) so the plugin stays adapter-agnostic. No SQL, no ORM-specific code. Use `internalAdapter` for core models, so database hooks run.
   - 9a. **No `connector` in where clauses.** Adapters group mixed `AND`/`OR` connectors differently (Kysely: all ANDs, then all ORs; the memory adapter folds left to right), so a mixed clause can match, and write, a different row. Write an OR as separate guarded writes, each fully ANDed (see `claimStatusLinkResend`). `src/tests/where-connectors.test.ts` fails if plugin source sets `connector`.
   - 9b. **The adapter must enforce `unique`.** Join recovers from duplicates through the unique index on `email`; no check-then-insert. The plugin warns at startup on the memory adapter, which doesn't enforce it.
   - 9c. **Inside a native transaction, never await the base adapter.** User creation runs in one, and on a single-connection driver (sqlite) the base adapter waits for the connection the transaction holds: a deadlock. Use the current adapter (`currentAdapter`, which `entries.ts` always does). Work that must survive the transaction's rollback runs in `withBaseAdapter` handed to `runInBackground` (see the blocked sign-up join). `transaction-pin.test.ts` pins the behaviour.

## Public endpoints

10. **No email enumeration.** Public (unauthenticated) endpoints return the same response shape, status and timing class whether or not an email is on the list, already approved, or already a user. "Join" on an existing entry is an idempotent success. Anything that reveals Status or Position to a caller requires proof of the email (a session, or a token sent to it).
11. **Rate-limit public endpoints** with the plugin's `rateLimit` rules (`max`, not `limit`). Tests that check rate limits must turn rate limiting back on (`getTestInstance` disables it).
12. Admin endpoints check the role server-side on an authoritative session (`sensitiveSessionMiddleware` / `getAuthoritativeSessionFromCtx`), never on a cached cookie session, and read the role from the user row in the database, not from the session's user snapshot. Every manager endpoint puts `managerMiddleware(opts)` in `use`. `src/tests/manager-access.test.ts` lists a sample request per `/waitlist/admin/*` path and fails when an endpoint is missing from it, so a new manager endpoint gets the 401 / 403 / allowed checks.
13. Endpoints follow Better Auth conventions: kebab-case paths under `/waitlist/`, only GET (query) or POST (body), mutations are POST, `zod/mini` schemas (rule 25) with `.meta({ description })` on every body and query field.

## Options, errors, types

14. **Every option is wired and tested.** An option that exists in `WaitlistOptions` has an effect in code and a test that fails if the effect is removed. No option is documented but ignored. Defaults live in one `opts` object.
    14a. **Host code never changes a public response or leaks a secret.** Callbacks run through `notifyHost`; nothing else calls `runCallback`, which a source guard checks. Host functions that answer a question (`bypass`, `validate`, `autoApprove`, `canManage`, `canonicalizeEmail`) run through `askHost`: a throw is logged, redacted, and counts as the fail-closed answer. Both take one scope (`{ context, ctx, opts, name, secrets }`) and add the request's secrets themselves (`requestSecrets`: the invite header and cookie, the query token, and every credential field of the body, passwords included); a new credential-carrying body field goes in `CREDENTIAL_FIELDS`. `host-functions.test.ts` covers every function-typed option (a `Record`, so a new one is a type error until it has a case); its source guard follows the options through aliases (destructuring, groups, element access, `.call` / `.apply` / `.bind`, renamed or typed parameters) and fails if a host function option is called or handed on as a value anywhere but inside the function passed to `askHost` or `notifyHost`. A host function asked on a public path is asked the same number of times on every branch, so its timing doesn't tell them apart (`referral.canonicalizeEmail` is asked twice for every join with a code, known or not).
    14b. **Referral successes are claimed once, on the referred row.** The referrer is read before the claim; the claim is one guarded `incrementOne` (`referralSucceeded = false`, `referredById` as read); only the caller whose write applied calls `onReferralSuccess`, and nothing that runs after the claim may stop that call (a failed read is logged and falls back), nor make the request fail. Nothing writes the referrer's row. `referralCount` is derived. The plugin never rewards on its own.
15. **Errors via `defineErrorCodes`** (`@better-auth/core/utils/error-codes`), in one `error-codes.ts`. Set it as `$ERROR_CODES` on both the server and the client plugin and re-export it from `./client`. No string error messages thrown inline. `error-codes.ts` imports nothing else, because `./client` ships it; the server-only `waitlistError()` (code to `APIError` with its status) lives in `errors.ts`.
16. **Server/client split.** `src/client.ts` imports server code with `import type` only. Nothing in `./client` may pull a server module into a client bundle: the client graph may import only `@better-auth/core/utils/error-codes` (rule 25 has the check). `./types` (`src/types.ts`) is `export type` only.
17. Keep the registry augmentation (`BetterAuthPluginRegistry`) and `satisfies BetterAuthPlugin` / `satisfies BetterAuthClientPlugin` on the plugin objects.

## Tests

18. **Test through the public API with `createWaitlistInstance` from `src/tests/harness.ts`** (a wrapper around `getTestInstance` from `better-auth/test`). Drive behaviour with `auth.api.*` and the client (`client.signUp.email`, ...), assert on responses, `error.status` and `error.code`. Do not import internal helpers into tests or assert on private functions or table internals.
19. Each user-creation path the gate claims to cover gets a test (at least email/password and one social provider, mocked with `msw`).
20. `getTestInstance` signs up a test user by default, which the gate will block: pass `{ disableTestUser: true }` or admit the test email explicitly.
21. Type-level behaviour (client inference) is tested in `*.test-d.ts` with `expectTypeOf`.

## Package hygiene

22. Every user-visible change ships a changeset (`pnpm changeset`). Breaking changes are `major`.
23. `build` (tsdown + publint strict + the client-graph and declaration checks), `typecheck`, `test`, `lint`, `lint:package` and `lint:types` pass; CI runs them on every PR, and the tests also on the Better Auth 1.7.0 floor and the latest 1.7.x.
24. No host-app concepts: this is a public, generic library, and nothing in it may assume what a host application does with its users (bookings, organizations, billing, ...). Runtime deps stay minimal; `better-auth` and `@better-auth/core` are peers.
25. **`zod/mini` only, and no zod in `./client`.** Runtime code imports `import * as z from "zod/mini"` and uses its functional API (`z.optional(z.string().check(z.maxLength(100)))`). Full `zod`, `zod/v4`, `zod/v3` and `zod/v4/core` are banned by `no-restricted-imports` in the `lint` block of `vite.config.ts`. Test files are exempt, because host validators in tests stand in for host code, which may use full zod. `./client` must not import zod at all: `build` runs `scripts/check-client-graph.mjs`, which fails if anything reachable from `dist/client.mjs` imports zod, `better-call` or any package but `@better-auth/core/utils/error-codes`, if `dist/types.mjs` has code, or if the client is over its gzip budget (2.5 kB; raise it only on purpose, saying why in the PR).
26. **Client code targets broad browser support: no ES2022-or-later built-ins.** Everything `./client` ships (`src/client.ts`, `src/redirect-errors.ts`, `src/error-codes.ts`, `src/version.ts`) runs in hosts' browsers, including older Safari. Use `Set`/`Map` or `Object.prototype.hasOwnProperty.call` instead of `Object.hasOwn`, index arithmetic instead of `.at()`, and so on. The client-graph check (rule 25) fails on `Object.hasOwn`, `Object.groupBy`, `Map.groupBy`, `Promise.withResolvers` and calls to `.at()`, `.findLast()`, `.findLastIndex()`, `.toSorted()`, `.toReversed()`, `.toSpliced()`, and also on `require()` and on any `import()` whose specifier isn't a string literal. Server code (Node 20+) is exempt.
